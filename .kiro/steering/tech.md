# 技術スタック定義

> **重要**: このプロジェクトはまだ設計フェーズであり、コードは存在しない。
> 以下の「確定」以外の項目は**未確定**であり、確定前提で実装を進めてはいけない。
> 不明な点は推測せず確認する。

## コスト制約（最重要・全判断に適用）

**月額 1,000円以内（約 $6〜7）を上限とする。**

技術選定・設計・実装のすべての判断でこの上限を超えないか検討すること。
超える可能性がある選択をする場合は、実装前に必ず理由と概算を提示して確認を取る。

### 絶対に踏んではいけない構成（単独で予算を超える）

- **VPC を作らない。** Lambda や SSR compute を VPC に入れると NAT Gateway が必要になり
  約 $35〜45/月（予算の5倍以上）。DynamoDB は HTTPS で到達できるため VPC は不要
- **ALB を使わない**（約 $18/月）。ECS / EC2 構成は採用しない
- **常時起動の DB インスタンスを置かない**（RDS / Aurora プロビジョンド: $15〜50/月）
- **RDS Proxy を使わない**（約 $15/月）
- **Secrets Manager を使わない**（$0.40/シークレット/月）。SSM Parameter Store (Standard) は無料

### 見落としやすいコスト

- **CloudWatch Logs の保持期間は既定で「無期限」。** ロググループ作成時に必ず
  retention（7〜14日）を明示設定する。設定漏れは静かに課金が増え続ける
- **Amazon Bedrock（将来のAI機能）が最大のリスク。** 使い方次第で単独で月1,000円を超える。
  AI機能は必ず「呼び出し回数上限」「モデル選定」「トークン数見積もり」をセットで設計する
- **画像配信**（将来の料理写真）。S3 保存は安いが CloudFront 転送量が効く。
  アップロード時にリサイズ・圧縮して配信サイズを抑える
- **DynamoDB の Scan 乱用**。Query で済む処理を Scan で書かない
- **Lambda のメモリ設定とタイムアウト**。過大な設定は無駄な課金になる
- **API Gateway は REST API ではなく HTTP API を使う**（REST API は約3.5倍高い）

## 確定事項

### クラウド

- **AWS** に統一する（完全AWS構成）
- 月額1,000円以内を目標上限とする（上記「コスト制約」参照）

### データベース

- **Amazon DynamoDB（オンデマンド）** を採用。シングルテーブル設計
- 採用理由:
  - コールドスタートがない。Aurora Serverless v2 は min 0 ACU で停止できるが、
    **24時間以上停止すると復帰に30秒以上かかる**ため「毎日面倒なく使える」に反する
  - VPC 不要 → NAT Gateway を踏まない
  - 「ユーザーが自由に追加できる生活習慣」のようなスキーマ可変要件に強い
- **アドホックな SQL 分析が必要になった場合**は、DynamoDB の S3 エクスポート機能
  （RCU消費なし）を使い、Athena または手元の DuckDB で分析する
- **重要な設計方針**: 食事記録の栄養値（kcal / PFC）は**書き込み時にスナップショットとして
  保存する**。食品マスタを参照する設計にしてはいけない。マスタ編集で過去の記録が
  遡って書き換わるのを防ぐため

### 認証

- **Amazon Cognito** を採用
- 初期は開発者自身のみが利用するが、Cognito 前提で複数ユーザー対応の土台を作る

### アーキテクチャ

**サーバーレス中心。VPC は作らない。**

```
[ブラウザ / スマートフォン]
   ↓
CloudFront + S3（静的SPA配信・OAC経由）
   ↓
API Gateway (HTTP API) + Cognito Authorizer  ← JWT検証をインフラで強制
   ↓
Lambda (TypeScript)
   ↓
DynamoDB（オンデマンド・シングルテーブル）
```

**Amplify Hosting は採用しない。** 採用しなかった理由:
- SSR compute のコールドスタートが1〜3秒。CDN 配信なら0秒
- 認証の検証をアプリコードで書く必要があり、1箇所の書き忘れが情報漏洩になる
- ビルド分数・SSRリクエスト・compute・転送の4軸課金でコスト予測性が低い

### 言語・フレームワーク

- **TypeScript** で統一する（フロント / Lambda / IaC すべて）
- フロントエンド: **Vite + React**
  - ルーティング: React Router
  - データ取得: TanStack Query
  - スタイル: **Tailwind CSS**
  - **PWA 化する**（`vite-plugin-pwa`）。スマホのホーム画面に置けることが
    「毎日面倒なく使える」に直接効くため
- **Next.js は採用しない。** 静的SPA構成では SSR / Server Components /
  Route Handlers が使えず、Next.js を選ぶ利点がないうえ static export の制約を背負うため
- IaC: **AWS CDK（TypeScript）**

### 認証の実装方針

- **サインイン方式: メール + パスワード**（Google フェデレーションは採用しない）
- Cognito Hosted UI + **Authorization Code Grant with PKCE**
- クライアントライブラリは `aws-amplify` の Auth モジュール
- **トークンを localStorage / sessionStorage に保存しない**（XSS で盗まれる）。メモリ保持
- JWT 検証は **API Gateway の Cognito Authorizer で行う**。Lambda はアプリコードで
  検証を書かず、claims から `sub` を受け取る
- **`userId` は必ず JWT の claims から取得する。リクエストボディやクエリから受け取らない**

### 栄養データの取得元

- **併用方針**: MVPはユーザーによる自前の食品マスタ登録のみ。公開栄養データベースの
  取り込みは後フェーズで実施する
- 後フェーズで取り込むのは **日本食品標準成分表（八訂）増補2023年（文部科学省）**
  - **公式APIは存在しない**。Excel形式のデータをダウンロードして自前DBにインポートする
  - 二次利用は自由。出典表記「日本食品標準成分表（八訂）増補2023年から引用」が必要
- 外部の栄養APIを実行時に呼び出す設計にはしない（コスト・可用性・日本データの欠如のため）
- 食品マスタは「可食部100gあたり」を基準値として保持し、分量換算はアプリ側で行う
- 外部由来データと自前登録データを区別できるスキーマにする

## 未確定事項

実装着手前に設計・提案・合意が必要な項目。

- **Cognito のサインイン方式**: メール/パスワード か Google フェデレーション か
  - 注意: `sub` は IdP ごとに異なる。PK が `USER#<sub>` なので後から変更すると
    データが孤立する。やり直しコストがある
- **独自ドメインを使うか**（Route 53 ホストゾーン $0.50/月）
- **AI API**: 利用するサービス（Amazon Bedrock 等）は AI機能フェーズで決定する
- **テスト構成**
- **コーディング規約・デザインシステム**（`.kiro/steering/_archive/` に別プロジェクト由来の
  未整備ファイルがある。LifePilot 用に書き直してから使う）

## コスト管理（重要要件・実装は後フェーズ）

以下は必須要件として扱うが、MVP完成後に実装する。

- 現在いくらかかっているかを常に確認できる仕組み
- 一定額を超えた場合の通知
- 一定額を超えた場合にシステムを停止する仕組み

注意点として、AWS には「請求額超過で自動的に全停止」する標準機能はない。
AWS Budgets + Budget Actions / Amazon SNS / Lambda を組み合わせた設計が必要で、
かつ完全な即時停止は保証されない。実装方針は別途設計する。

## 技術選定の判断基準

以下を重視して選定する。

1. **開発コスト**: 個人開発で管理可能な範囲に収める
2. **運用コスト**: アイドル時の課金を抑える
3. **将来の複数ユーザー対応**: 設計変更なしにスケールできること
4. **セキュリティ**: 認証・認可・データ分離を確実に行えること

## 技術的制約

### パフォーマンス目標

- ページロード: 初回2秒以内
- API応答: 平均1秒以内

### セキュリティ

- HTTPS通信必須
- 全ユーザー入力の検証必須
- 機密情報は SSM Parameter Store で管理し、コードにハードコードしない
  （Secrets Manager はコスト上使わない）
- ユーザーごとのデータ分離は PK（`USER#<sub>`）で行う
- **S3 バケットは非公開にし、CloudFront の OAC 経由でのみ配信する**

スマートフォン優先。モダンブラウザの最新2バージョンを対象とする。

- iOS Safari
- Android Chrome
- デスクトップ: Chrome / Firefox / Safari / Edge
