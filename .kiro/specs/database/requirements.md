# 要件定義書: database（データモデル基盤）

## 概要

LifePilot の全機能が共有する DynamoDB シングルテーブルのデータモデルを定義し、テーブルを構築する。

**この Spec の `design.md` はデータモデルの SSOT（Single Source of Truth）である。**
各機能 Spec の Data Models セクションは `design.md` を参照し、構造を書き写さない。

## スコープ

**含む**

- キー設計（PK / SK の命名規則）
- アクセスパターンの定義
- 全エンティティの構造定義（将来追加予定のものを含む）
- CDK による DynamoDB テーブルの構築

**含まない**

- 各エンティティの CRUD 実装（各機能 Spec で行う）
- アプリケーションコード全般
- 認証基盤（`auth-login` Spec で行う）

## 用語

- **PK**: パーティションキー
- **SK**: ソートキー
- **エンティティ**: 食事・体重・運動・目標などのデータ種別
- **PFC**: タンパク質（Protein）・脂質（Fat）・炭水化物（Carbohydrate）
- **PITR**: Point-in-Time Recovery（継続的バックアップ）

## 要件1: ユーザー単位のデータ分離

### ユーザーストーリー

**As a** 将来的に知人と共用される可能性があるアプリの利用者
**I want** 自分の生活データが他ユーザーから完全に分離されていること
**So that** 個人の食事・体重・生活記録が他人に見られない

### 受け入れ基準

1. データモデルは全アイテムをユーザー単位のパーティションに分離する
2. WHEN アイテムを書き込む場合、システムは認証済みトークンから取得したユーザー識別子を PK に使用する
3. IF リクエストボディまたはクエリパラメータからユーザー識別子を決定する設計が含まれる場合、これを設計違反として扱う
4. データモデルは1回のクエリで複数ユーザーのデータを取得できない構造である

---

## 要件2: 今日の状態を1回の問い合わせで取得できる

### ユーザーストーリー

**As a** 毎日スマートフォンからアプリを開く利用者
**I want** 今日の食事・体重・運動・睡眠がまとめて即座に表示されること
**So that** アプリを開いた瞬間に今日の状態を把握できる

### 受け入れ基準

1. データモデルは特定日の全エンティティを1回のクエリで取得できる
2. WHEN 日付を指定して問い合わせる場合、システムはその日のすべてのエンティティ種別を返す
3. データモデルはこの取得のために二次インデックスを必要としない

---

## 要件3: 期間指定でのデータ取得

### ユーザーストーリー

**As a** 体重や摂取カロリーの推移を確認したい利用者
**I want** 7日・30日・90日といった期間のデータを取得できること
**So that** グラフで推移を確認できる

### 受け入れ基準

1. データモデルは開始日と終了日を指定した範囲取得に対応する
2. WHEN 90日間を指定して問い合わせる場合、システムは結果を1回の問い合わせで返す
3. データモデルは全件走査（Scan）を必要としない

---

## 要件4: 過去記録の不変性

### ユーザーストーリー

**As a** 食品マスタを自分で編集する利用者
**I want** マスタを修正しても過去の食事記録が変わらないこと
**So that** 記録が信頼できる履歴として残る

### 受け入れ基準

1. 食事記録は栄養値（カロリー・PFC）を記録時点の確定値として保持する
2. WHEN 食品マスタの栄養値が変更される場合、システムは既存の食事記録の栄養値を変更しない
3. 食事記録は集計時に食品マスタを参照しない

---

## 要件5: 日付の基準が利用者の生活時間と一致する

### ユーザーストーリー

**As a** 日本在住の利用者
**I want** 記録の日付が日本時間の日付と一致すること
**So that** 朝食を記録したときに前日扱いにならない

### 受け入れ基準

1. データモデルは日付を日本標準時（JST）基準の `YYYY-MM-DD` 形式で保持する
2. IF UTC 基準で日付を決定する設計が含まれる場合、これを設計違反として扱う
3. 日付文字列はゼロ埋めされ、文字列としてソートしたときに日付順になる

---

## 要件6: 将来のエンティティ追加に対応する

### ユーザーストーリー

**As a** 段階的に機能を追加していく開発者
**I want** 睡眠・水分・カフェイン・自由習慣などを後から追加できること
**So that** テーブル定義の変更やデータ移行なしに機能を拡張できる

### 受け入れ基準

1. データモデルは新しいエンティティ種別の追加時にテーブル定義の変更を必要としない
2. WHEN 新しいエンティティ種別を追加する場合、既存エンティティのアクセスパターンは影響を受けない
3. キー命名規則は将来のエンティティ種別にも適用できる形式である

---

## 要件7: コスト上限を超えない

### ユーザーストーリー

**As a** 月1,000円以内で運用したい個人開発者
**I want** データストアのコストが予測可能で極小であること
**So that** 予算内で継続的に運用できる

### 受け入れ基準

1. テーブルはオンデマンド課金モードで作成される
2. システムは二次インデックス（GSI / LSI）を作成しない
3. システムは顧客管理型 KMS キーを使用しない（$1/月/キーが発生するため）
4. システムは Contributor Insights を有効にしない
5. WHERE アドホックな SQL 分析が必要な場合、システムは S3 エクスポート機能を使用する
   （このため PITR を有効にする）

---

## 要件8: データの誤削除から保護される

### ユーザーストーリー

**As a** 数か月分の生活データを蓄積していく利用者
**I want** 操作ミスやコード不備でデータが失われないこと
**So that** 蓄積した記録を安心して積み上げられる

### 受け入れ基準

1. テーブルは削除保護が有効な状態で作成される
2. テーブルは PITR が有効な状態で作成される
3. IF インフラコードがテーブルを破棄する操作を含む場合、システムはテーブルを保持する
   （RemovalPolicy: RETAIN）
