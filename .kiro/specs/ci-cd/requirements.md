# 要件定義書: ci-cd（品質ゲートと自動化）

## 概要

コードの品質・セキュリティ・コストに関する規約を、**ドキュメント上の約束から自動検査へ移す。**

このプロジェクトでは `.kiro/steering/` に多くの規約を定めているが、現在それらを守っているか
確認する仕組みがない。規約は人が覚えている限りしか機能せず、いずれ破られる。

## スコープ

**含む**

- ローカルでの自動チェック（git hooks、エディタ設定）
- CI での自動チェック（GitHub Actions）
- 静的解析（ESLint / Prettier / TypeScript）
- 依存の脆弱性チェックと自動更新
- 機密情報の混入検査
- IaC のセキュリティ検査
- **予算上限を守るための禁止リソース検査**

**含まない**

- **デプロイの自動化**（フロントエンド / Lambda / CDK いずれも）
  - デプロイ対象がまだ DynamoDB テーブル1つしかなく、実体ができてから設計するほうが
    実構成に合う。予算事故の主要な発生源でもあるため、範囲を絞る
  - `auth-login` Spec の完了後に別 Spec として検討する
- リリース自動化、バージョニング、変更履歴生成
- E2E テスト基盤

## 参考にした既存実装

別プロジェクト `lollab` の構成を調査した。段階構成（保存時 → pre-commit → pre-push →
CI → 週次 → Dependabot）は踏襲するが、以下の弱点は再現しない。

| lollab の弱点                                                                      | 本 Spec での扱い                                   |
| ---------------------------------------------------------------------------------- | -------------------------------------------------- |
| ESLint の追加ルールが全て `warn` で、`--max-warnings` 未指定のため CI を落とさない | 警告も失敗として扱う                               |
| `npm audit` / `safety` が `continue-on-error: true` で実質ノーゲート               | 失敗させる。例外を設ける場合は理由を明示する       |
| ESLint 設定ファイルが `.mjs` と `.mts` で二重化                                    | 設定ファイルは1つだけにする                        |
| secret scanning が存在しない                                                       | 導入する（AWS 認証情報を扱うため lollab より重要） |
| ドキュメントと実装の記述がずれている（pre-push の audit レベル）                   | 設定値を単一の場所で管理する                       |
| テストが存在するのに CI で実行されない層がある                                     | 全パッケージのテストを CI で実行する               |

## 要件1: 規約違反がマージ前に検出される

### ユーザーストーリー

**As a** 一人で開発しており、レビュアーがいない開発者
**I want** 規約違反を人の記憶に頼らず自動で検出したい
**So that** 規約が時間とともに形骸化しない

### 受け入れ基準

1. CI は Pull Request と `main` / `develop` への push で実行される
2. WHEN 静的解析が違反を検出する場合、CI は失敗する
3. **IF 静的解析が警告のみを出力する場合も、CI は失敗する**
   （警告を放置できる状態にしない）
4. WHEN 型エラーが存在する場合、CI は失敗する
5. WHEN テストが失敗する場合、CI は失敗する
6. WHEN フォーマットが規約と異なる場合、CI は失敗する

---

## 要件2: 予算上限がコードで守られる

### ユーザーストーリー

**As a** 月1,000円以内で運用したい開発者
**I want** 高額なリソースが定義されたら自動で気づきたい
**So that** 1つの実装ミスで予算の数倍を請求されることがない

### 受け入れ基準

1. システムは合成された CloudFormation テンプレートに対して禁止リソース検査を行う
2. IF テンプレートに以下のリソース型が含まれる場合、検査は失敗する
   - NAT Gateway
   - Elastic Load Balancer（ALB / NLB / CLB）
   - RDS DB インスタンス / RDS DB クラスター
   - RDS Proxy
   - Secrets Manager シークレット
   - 顧客管理 KMS キー
3. IF DynamoDB テーブルが二次インデックス（GSI / LSI）を持つ場合、検査は失敗する
4. IF DynamoDB テーブルがオンデマンド課金でない場合、検査は失敗する
5. WHERE 禁止リソースが必要になった場合、検査の除外設定は理由の記述を伴う
6. 検査は CI とローカルの双方で実行できる

## 要件3: 機密情報の混入が防がれる

### ユーザーストーリー

**As a** AWS の認証情報を扱う開発者
**I want** 機密情報をコミットする前に止めてほしい
**So that** リポジトリに認証情報が残り続ける事故を防げる

### 受け入れ基準

1. システムはコミット前に機密情報らしい文字列を検査する
2. WHEN 機密情報らしい文字列が検出される場合、コミットは中断される
3. CI は履歴に対しても機密情報の検査を行う
4. IF 検査が誤検知する場合、除外設定で個別に許可できる

---

## 要件4: IaC のセキュリティ違反が検出される

### ユーザーストーリー

**As a** AWS インフラを CDK で構築する開発者
**I want** S3 の公開設定漏れや過剰な IAM 権限を自動で検出したい
**So that** 個人の生活データが意図せず公開される事故を防げる

### 受け入れ基準

1. システムは CDK スタックに対してセキュリティ検査を行う
2. WHEN セキュリティ検査が違反を検出する場合、CI は失敗する
3. IF 意図的に違反を許容する場合、抑制設定は理由の記述を伴う

---

## 要件5: 依存の脆弱性が把握・更新される

### ユーザーストーリー

**As a** 個人開発者
**I want** 依存パッケージの脆弱性と更新を自動で知りたい
**So that** 手動で追跡する手間なく安全性を保てる

### 受け入れ基準

1. CI は依存パッケージの脆弱性検査を行う
2. WHEN 一定以上の深刻度の脆弱性が存在する場合、CI は失敗する
3. システムは依存の更新を定期的に自動提案する
4. WHERE メジャーバージョン更新の場合、システムは自動提案を行わない
   （破壊的変更を手動で確認するため）
5. CI は定期実行により、コード変更がない期間も脆弱性を検査する

---

## 要件6: ローカルで早く失敗する

### ユーザーストーリー

**As a** 毎日コードを書く開発者
**I want** CI を待たずに手元で問題を知りたい
**So that** 修正のサイクルが短く保たれる

### 受け入れ基準

1. WHEN コミットする場合、システムは変更されたファイルのみを対象に検査する
   （全体検査による待ち時間を避けるため）
2. WHEN push する場合、システムは全体の型検査とテストを実行する
3. IF 検査が失敗する場合、コミットまたは push は中断される
4. ローカルの検査項目は CI の検査項目と矛盾しない
5. WHERE 緊急時には検査を明示的に回避できる（`--no-verify`）

---

## 要件7: 設定が二重管理されない

### ユーザーストーリー

**As a** 設定のずれによる混乱を避けたい開発者
**I want** 同じ規約が1箇所だけで定義されていること
**So that** ローカルと CI で挙動が食い違わない

### 受け入れ基準

1. 静的解析の設定ファイルは各ツールについて1つだけ存在する
2. CI とローカルは同じ設定ファイルを参照する
3. IF 設定値を変更する場合、変更箇所は1つで済む
4. ドキュメントに設定値を転記しない（参照のみとする）
